# Repository research: platform and operator workflows

Research date: 18 November 2026. Scope: four user-selected repositories. This report inspects their public source at immutable revisions; it does not run their code, install their dependencies, reproduce their model metrics, test live services, or claim a complete security audit. Repository instructions, embedded agent prompts and setup scripts were treated as source material, not execution instructions.

## Executive decision

The strongest engineering references in this group are **predictive-maintenance-mcp for evidence contracts and honest diagnostic claims**, and **PHAEMOS for operator workflow breadth**. Neither supplies a validated replacement for KerfPulse's completed-cut damage-risk model. CNC Guard offers useful workflow presentation but synthesizes its supposed NASA-style inputs and several displayed AI outputs. Dhanush's project performs actual saved-model inference, but trains on AI4I synthetic observations and classifies current failure rather than forecasting future CNC failure.

Use these projects to improve requirements and independently implement appropriate patterns. Do not import their datasets into KerfPulse's measured-data benchmark. Do not report their numbers as equivalent baselines, and do not copy unlicensed or reciprocally licensed source into a differently licensed product without resolving reuse terms.

## 1. CNC Guard Dashboard

### Implemented system and user journey

Express, Mongoose/MongoDB and Socket.IO back a React/Vite dashboard. Server registers machine, alert, booking, history, knowledge, chat, monitoring, production and webhook routes. It seeds an empty database, generates missing CSV data, then starts its HTTP server. Socket broadcasts are global rather than scoped to an authenticated asset subscription. These are source-confirmed mechanics, not deployment-tested behavior. [Server entry point, lines 6–61](https://github.com/Lokeshloki159/cnc-guard-dashboard/blob/600ef0dfb489dd0d54d9ac1cca21d22de60fa97d/server/index.js#L6-L61).

The frontend has live monitoring, AI diagnosis, analytics, history, knowledge, technician booking and production pages. Monitoring controls start/stop/reset one or all three hard-coded machines. Booking writes a database work order with technician, machine, priority, scheduled time and notes. This creates a visible sequence from alert to human response, which is a useful product-design reference. It does not establish actual technician availability or execution. [Monitoring routes](https://github.com/Lokeshloki159/cnc-guard-dashboard/blob/600ef0dfb489dd0d54d9ac1cca21d22de60fa97d/server/routes/monitoring.js#L5-L37), [booking persistence](https://github.com/Lokeshloki159/cnc-guard-dashboard/blob/600ef0dfb489dd0d54d9ac1cca21d22de60fa97d/server/routes/bookings.js#L15-L38).

### Data provenance: synthesized, not downloaded NASA telemetry

The generator produces three CSVs of 876 rows each using `Math.random()`, hand-chosen wear increments and programmed fault phases. Columns include three vibration values, acoustic RMS, motor current, wear, health, fault type and kurtosis. Time increments by two seconds. Fault-onset rows are manually set to 650, 400 and 550. Its “NASA PHM-style” description does not make these NASA measurements: no original NASA acquisition or checksum is used in this generator. [Generator, lines 1–45](https://github.com/Lokeshloki159/cnc-guard-dashboard/blob/600ef0dfb489dd0d54d9ac1cca21d22de60fa97d/server/generateNasaData.js#L1-L45), [remaining generated scenarios](https://github.com/Lokeshloki159/cnc-guard-dashboard/blob/600ef0dfb489dd0d54d9ac1cca21d22de60fa97d/server/generateNasaData.js#L47-L138).

At replay time, temperature is synthesized again; remaining life is computed from `(300 - wear_um) / 300 * 48`; confidence is a random value between roughly 75 and 95. Fault detection uses direct thresholds on wear, vibration RMS and kurtosis. There is no trained predictor in this path. Wear and fault labels are already supplied by the generator, so the displayed outputs cannot demonstrate detection of previously unknown physical faults. [Replay transformations, lines 87–108](https://github.com/Lokeshloki159/cnc-guard-dashboard/blob/600ef0dfb489dd0d54d9ac1cca21d22de60fa97d/server/nasaReplay.js#L87-L108), [threshold detection, lines 133–168](https://github.com/Lokeshloki159/cnc-guard-dashboard/blob/600ef0dfb489dd0d54d9ac1cca21d22de60fa97d/server/nasaReplay.js#L133-L168).

### AI, evaluation and operator trust

Chat selects canned responses by keywords and adds simulated latency. Its citations are fixed strings, not retrieval results. The diagnosis page defines fixed fault, confidence, evidence and prescription objects, plus fixed accuracy and knowledge-index counters. No training split, fitted artifact, held-out evaluation or confidence calibration was found in the inspected tree. This is a presentation prototype, not a scientific CNC baseline. [Canned chat, lines 3–57](https://github.com/Lokeshloki159/cnc-guard-dashboard/blob/600ef0dfb489dd0d54d9ac1cca21d22de60fa97d/server/routes/chat.js#L3-L57), [fixed diagnosis, lines 13–29](https://github.com/Lokeshloki159/cnc-guard-dashboard/blob/600ef0dfb489dd0d54d9ac1cca21d22de60fa97d/client/src/pages/AIDiagnosis.jsx#L13-L29), [fixed KPI cards](https://github.com/Lokeshloki159/cnc-guard-dashboard/blob/600ef0dfb489dd0d54d9ac1cca21d22de60fa97d/client/src/pages/AIDiagnosis.jsx#L140-L154).

### Reliability, access and costs

Code inspection identifies deployment gaps: unrestricted HTTP/Socket CORS, no authentication middleware before operational routes, all-booking reads, and globally emitted sensor updates. Replay timers advance process memory and swallow database failures; live displays can therefore continue when persistence fails. These are static findings, not attempted exploitation. Twilio WhatsApp calls require external credentials and service availability; free source does not make hosted messaging free. [Route registration/CORS](https://github.com/Lokeshloki159/cnc-guard-dashboard/blob/600ef0dfb489dd0d54d9ac1cca21d22de60fa97d/server/index.js#L14-L38), [persistence and emission](https://github.com/Lokeshloki159/cnc-guard-dashboard/blob/600ef0dfb489dd0d54d9ac1cca21d22de60fa97d/server/nasaReplay.js#L109-L132), [Twilio setup](https://github.com/Lokeshloki159/cnc-guard-dashboard/blob/600ef0dfb489dd0d54d9ac1cca21d22de60fa97d/server/whatsapp.js#L1-L18).

No automated test files or CI workflows were present in the inventoried revision. No code/data license was found. **KerfPulse decision:** study alert → evidence → booking → production-impact presentation; independently build against real events and qualified assessments. Reject synthetic telemetry, random confidence, invented RUL, fixed diagnosis, unauthenticated control routes and implied NASA provenance.

## 2. Dhanush Predictive Maintenance System

### Implemented inference and UI

This project has actual scikit-learn model inference. FastAPI exposes `/predict`, `/predict-batch` and `/metrics`. A saved joblib bundle contains model, feature names and evaluation metrics. React provides sample-prediction dashboard, CSV upload and model-metrics pages; the dashboard sends four hard-coded sensor profiles to the real predictor. Metrics are saved training-run results, not continuously measured field accuracy. [API routes](https://github.com/Dhanush-1213/predictive-maintenance-system/blob/e8436b9fb292f8e7572677931439c143eaeb25b7/backend/app/main.py#L32-L84), [bundle and prediction](https://github.com/Dhanush-1213/predictive-maintenance-system/blob/e8436b9fb292f8e7572677931439c143eaeb25b7/backend/app/ml/predictor.py#L5-L65), [sample inputs](https://github.com/Dhanush-1213/predictive-maintenance-system/blob/e8436b9fb292f8e7572677931439c143eaeb25b7/frontend/src/pages/Dashboard.jsx#L11-L61).

### Dataset and task boundary

Bundled `data/ai4i2020.csv` is AI4I 2020. UCI explicitly identifies it as synthetic: 10,000 observations, five continuous sensor/usage quantities plus product type, with failure mechanisms generated from formulas and random rules. Dhanush uses air temperature, process temperature, rotational speed, torque and tool wear, dropping IDs, type and failure-mode target columns. It predicts the current row's `Machine failure`, with no future horizon, no observed tool-life endpoint and no real CNC sensor-waveform provenance. [UCI dataset source](https://archive.ics.uci.edu/dataset/601/ai4i+2020+predictive+maintenance+dataset), [selected columns](https://github.com/Dhanush-1213/predictive-maintenance-system/blob/e8436b9fb292f8e7572677931439c143eaeb25b7/backend/train_model.py#L31-L53).

### Training, validation and limitations

Training uses an 80/20 stratified random row split, seed 42, and RandomForestClassifier with 200 trees, maximum depth 10 and balanced class weights. It reports accuracy, precision, recall, F1, ROC-AUC and impurity feature importances, then stores them with the model. Dropping failure sublabels avoids an obvious direct-target leakage route. However, the code contains no tool/machine/time-separated outer validation, probability calibration, cluster uncertainty, independent-site test or decision-utility evaluation. Random-row performance on this synthetic task cannot validate KerfPulse's cross-workpiece future-risk task. [Training and metrics, lines 55–112](https://github.com/Dhanush-1213/predictive-maintenance-system/blob/e8436b9fb292f8e7572677931439c143eaeb25b7/backend/train_model.py#L55-L98).

No numerical score is asserted here: the `.pkl` was intentionally not deserialized, and no retraining was run. The inference's health bands are hand-set at 30/70 percent. Recommendation text comes from separate deterministic temperature/torque/wear rules, not a trained causal fault diagnosis. A model's positive class and displayed health bands can disagree because they use different thresholds. [Health bands and recommendation rules](https://github.com/Dhanush-1213/predictive-maintenance-system/blob/e8436b9fb292f8e7572677931439c143eaeb25b7/backend/app/ml/predictor.py#L14-L40).

### Operational and security assessment

Single inputs are typed as unrestricted floats; no model-domain bounds or source qualification are declared. CSV handling checks filename and required columns, then reads and scores the file without explicit row/byte limits in the route. There is no authentication, database, immutable prediction history, IoT receipt protocol, streaming service or work-order state machine in the inspected tree. Frontend prediction failures primarily go to console; metrics can remain in a loading state after a failed request. [Input schema](https://github.com/Dhanush-1213/predictive-maintenance-system/blob/e8436b9fb292f8e7572677931439c143eaeb25b7/backend/app/schemas.py#L4-L18), [batch ingestion](https://github.com/Dhanush-1213/predictive-maintenance-system/blob/e8436b9fb292f8e7572677931439c143eaeb25b7/backend/app/main.py#L48-L84), [metrics error handling](https://github.com/Dhanush-1213/predictive-maintenance-system/blob/e8436b9fb292f8e7572677931439c143eaeb25b7/frontend/src/pages/Metrics.jsx#L18-L35).

The README itself lists streaming, authentication, Docker, persistence and notifications as future improvements. No automated tests were found in the tree. No repository code license was found; the UCI dataset's own terms are separate. **KerfPulse decision:** retain the clear single/batch input → result → metric visualization pattern, but keep measured data, typed bounded contracts, immutable lineage, calibrated semantics and source abstention. Do not add AI4I as evidence of real-machine predictive validity. [Declared future work](https://github.com/Dhanush-1213/predictive-maintenance-system/blob/e8436b9fb292f8e7572677931439c143eaeb25b7/README.md#L335-L345).

## 3. Predictive Maintenance MCP

### Architecture and end-user purpose

This is a reliability-engineer tool server, not a multi-tenant CNC fleet SaaS. Its orchestration registers acquisition, analysis, diagnosis, reporting, prognosis, asset and import tools. Signal processing is separated from protocol plumbing. Engineer-supplied recordings become spectral/statistical evidence, severity assessments and reports; a language-model client can call tools and explain results. MCP supplies interaction, not predictive validity. [Server registration](https://github.com/LGDiMaggio/predictive-maintenance-mcp/blob/2171f0969baef0c7aa3dbeb50846d2ccc0c7b63c/src/mcp_tools/__init__.py#L1-L24), [architecture map](https://github.com/LGDiMaggio/predictive-maintenance-mcp/blob/2171f0969baef0c7aa3dbeb50846d2ccc0c7b63c/docs/architecture.md#L1-L62).

Useful implemented components include 17 time-domain features, envelope spectra, expected bearing-frequency tests, explicit evidence grades, indicator history/projection, and repeat-measurement threshold-crossing estimators. Bearing evidence is expressly not probability. RUL routines require repeated measurements and distinguish curve-fit R² from confidence in the future. These are directly relevant safeguards against misleading CNC dashboards. [Feature implementation](https://github.com/LGDiMaggio/predictive-maintenance-mcp/blob/2171f0969baef0c7aa3dbeb50846d2ccc0c7b63c/src/signal_processing/features.py#L20-L96), [bearing semantics](https://github.com/LGDiMaggio/predictive-maintenance-mcp/blob/2171f0969baef0c7aa3dbeb50846d2ccc0c7b63c/src/diagnostics/bearing_analyzer.py#L1-L14), [RUL preconditions](https://github.com/LGDiMaggio/predictive-maintenance-mcp/blob/2171f0969baef0c7aa3dbeb50846d2ccc0c7b63c/src/prognostics/rul_estimator.py#L1-L18).

### Two distinct real-data resources, different permissions

Bundled bearing examples contain 20 real single-channel acceleration recordings: 14 training files and six test files. Metadata declares rates of 97,656 or 48,828 Hz, durations six or three seconds, and corresponding sample counts. These are short condition-diagnosis recordings, not a CNC cutter run-to-failure cohort. The data originate with Eric Bechhoefer and are redistributed through MathWorks; **the repository's MIT code license does not apply to these samples**. Their notice specifies CC BY-NC-SA 4.0 and excludes commercial use without separate permission. [Data table](https://github.com/LGDiMaggio/predictive-maintenance-mcp/blob/2171f0969baef0c7aa3dbeb50846d2ccc0c7b63c/data/README.md#L66-L126), [separate data license](https://github.com/LGDiMaggio/predictive-maintenance-mcp/blob/2171f0969baef0c7aa3dbeb50846d2ccc0c7b63c/data/LICENSE#L1-L32), [MIT code license](https://github.com/LGDiMaggio/predictive-maintenance-mcp/blob/2171f0969baef0c7aa3dbeb50846d2ccc0c7b63c/LICENSE#L1-L21).

A separate CWRU benchmark covers 60 fault records and four healthy baselines, with hashes, opaque IDs, separate label/scoring paths and reference diagnosability strata. These mechanics help prevent label filenames reaching analysis. This evaluates bearing evidence from short recordings; it does not evaluate five-cut CNC damage risk, RUL or maintenance economics. [Blind protocol](https://github.com/LGDiMaggio/predictive-maintenance-mcp/blob/2171f0969baef0c7aa3dbeb50846d2ccc0c7b63c/docs/benchmark-methodology.md#L22-L77).

### Important metric interpretation

The committed result reports, on 44 clearly diagnosable fault records: the labelled fault is supported on 44, another type is also supported on 44, and all 44 remain multiple-candidate outcomes with no single fault named. The labelled type appears first in 40/44. Of four normal recordings, three list bearing candidates and one singles out a fault. Therefore “100% fault support” must not become “100% diagnostic accuracy,” and the offline 40/44 ranking must not become an online classifier claim. These are repository artifacts, not independently reproduced results. [Current result explanation](https://github.com/LGDiMaggio/predictive-maintenance-mcp/blob/2171f0969baef0c7aa3dbeb50846d2ccc0c7b63c/README.md#L116-L138), [committed scoring definitions/results](https://github.com/LGDiMaggio/predictive-maintenance-mcp/blob/2171f0969baef0c7aa3dbeb50846d2ccc0c7b63c/benchmarks/cwru/results/results.json#L1-L120).

### Separate ML path: useful baseline, validation traps

`train_anomaly_model` extracts healthy-signal segments, fits StandardScaler and PCA, then fits OneClassSVM or novelty LOF. Optional faulty recordings guide hyperparameter search. This is a separate branch from the blind deterministic bearing benchmark. In its fallback healthy-validation path, the 80/20 split occurs **after** scaler and PCA have fit all healthy features. Thus preprocessing has seen the validation partition. Splitting stacked segments also does not guarantee held-out source recordings, particularly with overlap. [Preprocessing before split](https://github.com/LGDiMaggio/predictive-maintenance-mcp/blob/2171f0969baef0c7aa3dbeb50846d2ccc0c7b63c/src/mcp_tools/diagnostics_tools.py#L472-L489), [later fallback split](https://github.com/LGDiMaggio/predictive-maintenance-mcp/blob/2171f0969baef0c7aa3dbeb50846d2ccc0c7b63c/src/mcp_tools/diagnostics_tools.py#L727-L753).

Fault validation records can be reused to select hyperparameters and then calculate displayed validation scores. No separate final test set is enforced by that routine. LOF's fallback branch does not perform the OneClassSVM-specific retraining on the first 80% before scoring the final 20%. These are static code findings, not evidence that the independent CWRU benchmark has the same flaw. KerfPulse must split recordings/tools/workpieces before any learned preprocessing and separate tuning from final evaluation. [Selection loop](https://github.com/LGDiMaggio/predictive-maintenance-mcp/blob/2171f0969baef0c7aa3dbeb50846d2ccc0c7b63c/src/mcp_tools/diagnostics_tools.py#L526-L564), [final validation](https://github.com/LGDiMaggio/predictive-maintenance-mcp/blob/2171f0969baef0c7aa3dbeb50846d2ccc0c7b63c/src/mcp_tools/diagnostics_tools.py#L759-L795).

### Evidence lineage, security and testability

Its asset ledger records declarations, measurements and derived snapshots as append-only events with content-derived IDs and lock-protected writes. Comparability distinguishes contradictory metadata from absent metadata and records reasons for changes in unit, direction, speed or acquisition context. Import attestation records who claimed a value and its evidence basis while explicitly refusing to equate tool-call assertions with authenticated identity. These are valuable prior implementations: lineage, domain qualification and restrained claims alone are not novel contributions for KerfPulse. [Ledger invariants](https://github.com/LGDiMaggio/predictive-maintenance-mcp/blob/2171f0969baef0c7aa3dbeb50846d2ccc0c7b63c/src/asset_ledger/store.py#L1-L104), [comparability](https://github.com/LGDiMaggio/predictive-maintenance-mcp/blob/2171f0969baef0c7aa3dbeb50846d2ccc0c7b63c/src/asset_ledger/comparability.py#L1-L35), [attestation boundary](https://github.com/LGDiMaggio/predictive-maintenance-mcp/blob/2171f0969baef0c7aa3dbeb50846d2ccc0c7b63c/src/signal_import/attestation.py#L1-L47).

Remote deployments rely on reverse-proxy authentication; the server does not identify tenants itself. Network signal-file access defaults closed, with an explicit opt-in that is not authentication. Docker's sample publishes port 8000 and binds the service on all interfaces, so it must not be exposed unchanged. The substantial test tree covers diagnostics, import, benchmark guards and security contracts, but this review did not run it or verify its claimed coverage. Self-hosted signal processing can avoid hosted-model fees; choice of external LLM client can add costs. [Deployment authentication boundary](https://github.com/LGDiMaggio/predictive-maintenance-mcp/blob/2171f0969baef0c7aa3dbeb50846d2ccc0c7b63c/docs/DEPLOYMENT.md#L382-L390), [network opt-in caveat](https://github.com/LGDiMaggio/predictive-maintenance-mcp/blob/2171f0969baef0c7aa3dbeb50846d2ccc0c7b63c/docs/DEPLOYMENT.md#L531-L545), [Compose defaults](https://github.com/LGDiMaggio/predictive-maintenance-mcp/blob/2171f0969baef0c7aa3dbeb50846d2ccc0c7b63c/docker-compose.yml#L14-L42).

**KerfPulse decision:** adopt evidence-basis UX, unit/rate declaration, blinded benchmark guards and hypothesis-vs-probability distinctions. Keep plant authentication and scope enforcement in KerfPulse. Do not attach generic bearing diagnosis or ISO zones to CNC tool wear without an applicable sensor/asset contract; this repository itself records standard-version and machine-power scope caveats. [Severity scope/provenance](https://github.com/LGDiMaggio/predictive-maintenance-mcp/blob/2171f0969baef0c7aa3dbeb50846d2ccc0c7b63c/src/diagnostics/iso20816.py#L1-L34).

## 4. PHAEMOS

### System breadth and real-data status

PHAEMOS is genuinely an industrial IoT platform reference. It includes FastAPI/SQLAlchemy/PostgreSQL, a Next.js dashboard, device administration, telemetry, anomaly alerts, tickets, maintenance windows, audit, webhooks, multi-board firmware and a Rust edge forwarder. The project's own current boundary is explicit: software runs with a simulator; physical nodes and training on real readings remain unfinished. No measured production CNC training dataset or verified model benchmark was supplied by the inspected files. [Current status](https://github.com/phaemos/phaemos/blob/c54f922b442c7813516ce4cc8c1bab933970716c/README.md#L9-L18), [registered routes](https://github.com/phaemos/phaemos/blob/c54f922b442c7813516ce4cc8c1bab933970716c/backend/app/main.py#L54-L70), [physical-data checklist](https://github.com/phaemos/phaemos/blob/c54f922b442c7813516ce4cc8c1bab933970716c/docs/VERIFICATION.md#L239-L247).

Telemetry supports temperature, humidity, pressure, three accelerometer and gyro axes, current/voltage/power, shaft RPM/angle, sound and other board-specific quantities. Most fields are optional floats; the protocol carries derived readings rather than a synchronized high-frequency CNC waveform. Simulator uses Gaussian random draws around configured means and ramps fault factors over the requested run. This cannot satisfy KerfPulse's real-measurement requirement. [Input schema](https://github.com/phaemos/phaemos/blob/c54f922b442c7813516ce4cc8c1bab933970716c/backend/app/schemas/telemetry.py#L6-L63), [simulator](https://github.com/phaemos/phaemos/blob/c54f922b442c7813516ce4cc8c1bab933970716c/client/python/phaemos_client/simulator.py#L18-L41).

### ML path and failure semantics

The shared ML service trains a 200-tree Isolation Forest with contamination 0.05 and seed 42. It fits a general model plus node-type models when a node has at least 50 rows and enough field coverage. Score normalization maps its decision boundary to 0.7. These normalized anomaly scores are not calibrated probabilities of impending failure. Missing fields become zero in the matrix. If no model exists, scoring returns `(0.0, False)`; for KerfPulse that would conceal unavailable inference as normal health, so retain explicit unavailable/abstention instead. [Training and normalization](https://github.com/phaemos/phaemos/blob/c54f922b442c7813516ce4cc8c1bab933970716c/backend/app/services/ml_service.py#L20-L105), [missing-model behavior](https://github.com/phaemos/phaemos/blob/c54f922b442c7813516ce4cc8c1bab933970716c/backend/app/services/ml_service.py#L108-L130).

The retrain job selects the most recent 10,000 telemetry rows across the database, trains and overwrites one model bundle. The cooldown is process memory. No per-asset qualification, held-out selection gate, atomic version promotion or prospective drift acceptance is enforced in that job. Training on mixed faulty/recent conditions can normalize degradation unless data are curated. Evaluation accepts a labelled CSV and computes precision/recall/F1, but does not itself establish train/test separation. The standalone rolling-feature helper is not called by the shared train or score service, so it should not be counted as deployed temporal modeling. [Retraining](https://github.com/phaemos/phaemos/blob/c54f922b442c7813516ce4cc8c1bab933970716c/backend/app/routes/ml.py#L17-L81), [evaluation](https://github.com/phaemos/phaemos/blob/c54f922b442c7813516ce4cc8c1bab933970716c/backend/ml/evaluate.py#L75-L105), [standalone feature helper](https://github.com/phaemos/phaemos/blob/c54f922b442c7813516ce4cc8c1bab933970716c/backend/ml/preprocess.py#L1-L40).

### Strong operator workflow lessons

Three consecutive anomalous readings raise one model alert; three normal readings clear it. The service checks existing open inspection tickets and reuses/escalates one rather than creating a fresh ticket every reading. Maintenance windows suppress alerts during planned downtime. These are valuable alert-fatigue and workflow patterns. However, the comment's approximately 1/8,000 chance for three 5% flags assumes independent observations; correlated machine telemetry does not establish that field false-alarm rate. KerfPulse should measure event-level burden under real grouped trajectories rather than inherit the estimate. [Alert/ticket logic](https://github.com/phaemos/phaemos/blob/c54f922b442c7813516ce4cc8c1bab933970716c/backend/app/services/alert_service.py#L84-L163), [maintenance suppression](https://github.com/phaemos/phaemos/blob/c54f922b442c7813516ce4cc8c1bab933970716c/backend/app/routes/maintenance.py#L47-L64).

### Access and delivery: inspect boundaries, not feature labels

User authentication checks JWT type and database token version; admin dependencies protect administrative routes. Device routes implement technician ownership checks. However, telemetry reads/export/latest and anomaly history only require an authenticated user and filter by requested device ID; inspected WebSocket handshake checks token validity but not device ownership. This differs from the device-detail restriction. Treat this as a high-priority static scope-consistency concern, not proof of a live exploit or claim about an uninspected upstream deployment. [Token validation](https://github.com/phaemos/phaemos/blob/c54f922b442c7813516ce4cc8c1bab933970716c/backend/app/routes/auth.py#L133-L172), [device ownership](https://github.com/phaemos/phaemos/blob/c54f922b442c7813516ce4cc8c1bab933970716c/backend/app/routes/devices.py#L70-L85), [telemetry query](https://github.com/phaemos/phaemos/blob/c54f922b442c7813516ce4cc8c1bab933970716c/backend/app/routes/telemetry.py#L78-L160), [WebSocket handshake](https://github.com/phaemos/phaemos/blob/c54f922b442c7813516ce4cc8c1bab933970716c/backend/app/routes/ws.py#L20-L50).

Ingest resolves device from its API key and commits reading plus model result before evaluating alerts. Alerting and WebSocket delivery occur afterwards, outside a transactional outbox, so a crash can preserve a reading while losing a notification. WebSocket subscribers are process-local; the file explicitly limits this to one worker. No receipt ID/sequence deduplication exists in the inspected telemetry route. The CSV export first loads all rows and builds the entire CSV in memory despite its streaming response wrapper. [Ingest ordering](https://github.com/phaemos/phaemos/blob/c54f922b442c7813516ce4cc8c1bab933970716c/backend/app/routes/telemetry.py#L23-L75), [subscriber limitation](https://github.com/phaemos/phaemos/blob/c54f922b442c7813516ce4cc8c1bab933970716c/backend/app/services/ws_manager.py#L1-L10), [export buffering](https://github.com/phaemos/phaemos/blob/c54f922b442c7813516ce4cc8c1bab933970716c/backend/app/routes/telemetry.py#L92-L120).

Rust forwarder appends and syncs pending JSON lines, sends them in order, and rewrites the remaining queue after successful HTTP responses. But replay after server commit/before acknowledgment can duplicate readings without server-side deduplication. Its retry loop is driven by new stdin lines; if an outage occurs and input stops, recovery does not independently drain existing backlog. No hard byte/row spool cap is enforced in the inspected source. Retain KerfPulse's bounded spool, receipt matching and semantic deduplication. [Forwarding loop](https://github.com/phaemos/phaemos/blob/c54f922b442c7813516ce4cc8c1bab933970716c/edge/src/main.rs#L39-L109), [disk queue](https://github.com/phaemos/phaemos/blob/c54f922b442c7813516ce4cc8c1bab933970716c/edge/src/spool.rs#L29-L80).

### Deployment, licenses and reuse decision

Compose includes PostgreSQL/Redis/backend/frontend and loopback port bindings, but uses explicit development credentials and environment. Source tests cover auth, tokens, devices, telemetry, anomalies and ML; their presence is verified, not their passing status. Software is AGPL-3.0-or-later and hardware CERN-OHL-S-2.0, according to its own licensing notice. Keep this distinction in any dependency/reuse decision. Physical hardware, hosting, messaging and email integrations can add cost even when self-hosted software is open source. [Development Compose](https://github.com/phaemos/phaemos/blob/c54f922b442c7813516ce4cc8c1bab933970716c/infra/docker-compose.yml#L5-L55), [licensing scope](https://github.com/phaemos/phaemos/blob/c54f922b442c7813516ce4cc8c1bab933970716c/NOTICE.md#L1-L31).

**KerfPulse decision:** independently implement maintenance windows, deduplicated inspection tasks, ticket linkage and explicit connection-state UX. Keep unavailable-model abstention, exact asset authorization, server-side event identity, transactional outbox and immutable versioned model promotion. Do not substitute simulator anomalies for measured future-failure validation.

## Novelty and research implications

These references already implement or describe fusion-like multi-sensor presentation, anomaly detection, evidence lineage, import qualification, human maintenance workflow and natural-language assistance. None alone is a defensible new research contribution for KerfPulse. The useful research question remains whether a **causal, budgeted acquisition policy aligned with first feasible maintenance action** improves decision utility over current-only, full-fusion and simple scheduled baselines under grouped evaluation. Repository review supplies design constraints; it supplies no positive experiment result for that question.

Do not move to a more complex model merely because a reference names AI or RUL. First resolve KerfPulse's observed premature-first-inspection objective mismatch, keep existing artifacts immutable, freeze exploratory changes before execution, and confirm on an independent machine/cohort before claiming generalization or commercial utility.
